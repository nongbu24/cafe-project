# 작업 실행 가이드

이 문서는 `AGENTS.md`가 정한 작업 경로를 실제로 진행하는 방법과 권장 체크리스트를 설명한다.
독립된 강제 규칙을 추가하지 않으며 승인과 보호 작업의 기준은 `AGENTS.md`만 따른다.

---

## 1. 경로 선택

먼저 요청이 상태를 바꾸는지 확인한다.
설명, 분석, 리뷰와 상태 확인처럼 아무 상태도 바꾸지 않는 작업은 필요한 자료를 조사한 뒤 바로 보고한다.

변경이 필요하면 영향과 복구 가능성을 기준으로 경량·일반·보호 경로 중 하나를 선택한다.

| 예시 | 보통 선택할 경로 |
|---|---|
| 오타, 링크 문구, 주석, 포맷 수정 | 경량 |
| 범위가 명확한 설정값이나 단일 함수 수정 | 경량. 단, 보안·데이터·운영 영향이 있으면 보호 |
| 기능 추가, 여러 파일에 걸친 버그 수정 | 일반 |
| 일반적인 리팩터링과 의존성 변경 | 일반. 대규모 구조 변경이나 영향이 불명확하면 보호 |
| 보호 가능성이 있는 작업 | `AGENTS.md`의 보호 작업 기준에 따라 판단 |

파일 수만으로 경로를 기계적으로 결정하지 않는다.
여러 문서의 같은 용어를 고치는 단순 작업은 경량일 수 있고, 한 줄짜리 운영 설정 변경은 보호 작업일 수 있다.

---

## 2. 경량 경로

```text
요청 확인 → 수정 → 최소 검증 → 결과 보고
```

1. 요청한 결과와 수정 대상을 확인한다.
2. 대상 파일과 필요한 주변 문맥만 읽는다.
3. 요청 범위만 수정한다.
4. 변경에 맞는 가장 작은 검증을 실행한다.
5. 변경 내용과 검증 결과를 간단히 보고한다.

경량 작업에는 별도 계획 문서, 작업 기록, 상태 값이나 마감 절차가 필요하지 않다.
수정 중 영향이 여러 영역으로 퍼지거나 보호 작업이 필요하다는 사실을 발견하면 해당 경로로 전환한다.

검증 예시는 다음과 같다.

- 문구 수정: 변경 문장과 링크 확인
- 포맷 수정: 포매터 또는 `git diff --check`
- 단일 함수 수정: 해당 함수의 대상 테스트
- 간단한 설정 수정: 파서·린터 또는 관련 실행 확인

---

## 3. 일반 경로

```text
짧은 계획 공유 → 사용자 승인 → 간단한 작업 기록 → 구현 → 검증 → 기록 마무리와 변경 요약
```

### 짧은 계획

대화에서 다음 내용만 작업에 필요한 수준으로 공유한다.

- 해결할 문제와 원하는 결과
- 주로 변경할 영역
- 구현 방향
- 실행할 검증
- 사용자가 알아야 할 중요한 제한이나 선택지

해당 내용이 없으면 억지로 빈 항목을 만들지 않는다.
상세한 별도 계획 문서는 만들지 않고, 승인받은 계획의 핵심만 간단한 작업 기록에 옮긴다.

### 작업 기록 시작

계획 승인 후 `docs/templates/task-log.md`를 참고하여
`docs/dev/tasks/YYYYMMDD-{영문 소문자 kebab-case 작업명}.md`를 만든다.
작업 목적과 변경 범위, 간단한 계획만 먼저 적고 구현을 시작한다.

### 구현

- 승인된 결과를 만드는 데 필요한 파일만 변경한다.
- 현재 작업 트리에 기존 변경이 있으면 승인 범위와 구분하여 보존한다.
- 구현 중 확인된 작은 세부 사항은 승인된 방향 안에서 해결한다.
- 공개 계약이나 현재 기능 동작이 바뀌면 그 사실을 설명하는 원본 문서를 함께 갱신한다.

목표나 주요 범위가 바뀌면 새 짧은 계획을 공유한다.
`AGENTS.md`의 보호 작업이 필요해지면 일반 작업을 멈추고 보호 경로의 영향 분석과 승인을 진행한다.

### 검증과 보고

변경한 동작을 직접 확인하는 테스트나 수동 확인을 우선하고, 프로젝트 프로필의 관련 명령을 실행한다.
작업 기록의 「변경 결과」와 「검증과 남은 사항」을 실제 결과로 마무리한 뒤 사용자에게 보고한다.
최종 보고는 다음 내용이면 충분하다.

- 핵심 변경과 주요 파일
- 실행한 검증과 결과
- 실행하지 못한 검증과 이유
- 남은 제한사항이나 필요한 사용자 조치

## 4. 보호 경로

보호 작업의 정확한 목록과 승인 규칙은 `AGENTS.md`의 「보호 작업」을 참조한다.
이 문서에는 같은 목록을 다시 복사하지 않는다.

### 영향 분석과 계획

실행 전에 다음 내용을 구체적으로 확인한다.

- 실행할 작업 또는 명령
- 대상 환경과 대상 데이터·파일·서비스
- 예상 영향과 영향 범위
- 백업, 롤백 또는 다른 복구 방법
- 복구할 수 없는 부분
- 실행 전후 검증 방법과 성공 기준

이 정보가 확정된 상태에서 실행 직전 승인을 한 번 받는다.
승인 후 대상이나 영향이 달라지면 변경된 부분을 설명하고 다시 승인받는다.

### 실행과 기록

- 복구 수단을 먼저 확보하거나 복구 불가능성을 승인 내용에 포함한다.
- 여러 단계 작업이 일부만 성공하면 자동으로 반복하지 않고 현재 영향을 먼저 확인한다.
- 운영·공유 환경에서는 대상 환경을 다시 확인한 뒤 실행한다.
- 실행 결과와 사후 검증을 `docs/dev/tasks/`의 작업 기록에 남긴다.
- 프로젝트의 기존 이슈·PR·변경 기록이 있으면 작업 기록에서 링크한다.

보호 작업 기록에는 승인된 대상과 영향, 복구 수단, 실제 실행 내용, 결과와 미해결 항목을 남긴다.
원시 로그 전체나 민감 값은 기록하지 않는다.

## 5. 검증 선택

검증은 형식을 채우기 위한 단계가 아니라 변경 결과를 신뢰할 수 있게 만드는 수단이다.

| 변경 위험 | 권장 검증 |
|---|---|
| 낮음 | 변경 내용 직접 확인, 포맷·문법 검사 |
| 보통 | 대상 테스트, 타입 검사·린트, 관련 diff 검토 |
| 높음 | 대상 검증과 프로젝트 기본 검증, 영향 영역 회귀 검사 |
| 보호 작업 | 실행 전 상태 확인, 실행 결과 확인, 복구 가능성 또는 롤백 검증 |

- 실행한 명령, 종료 결과와 중요한 확인 내용을 보고한다.
- 자동 검증이 없으면 정적 검토나 수동 확인을 사용하고 그 한계를 밝힌다.
- 실패하면 원인을 확인하고 승인된 범위 안에서 수정한다.
- 같은 원인과 같은 접근을 근거 없이 반복하지 않는다.
- 외부 환경이나 권한 때문에 검증할 수 없으면 미검증 항목과 필요한 사용자 조치를 보고한다.
- `git status`와 diff 검토는 기존 사용자 변경과 범위 밖 변경을 구분할 필요가 있을 때 사용한다.

`PASS`, `FAIL`, `BLOCKED` 같은 상태 이름이나 Attempt 번호는 필요한 프로젝트가 선택적으로 사용할 수 있지만 공통 완료 조건은 아니다.

## 6. Git 작업

커밋이나 푸시 요청을 받으면 현재 브랜치, 변경 범위와 민감 정보 포함 가능성을 먼저 확인한다.
요청·검증된 변경만 스테이징하고 관련 없는 기존 변경은 포함하지 않는다.

범위 지정 없이 `커밋해줘`라는 요청을 받으면 다음 순서로 진행한다.

1. 추적·미추적 파일을 포함한 작업 트리 전체와 diff를 확인한다.
2. 변경을 파일 수가 아니라 목적과 의존 관계를 기준으로 논리 단위 목록으로 나눈다.
3. 기반 구조, 도메인 모델, 외부 연동, 공개 API처럼 독립적으로 설명·검증 가능한 목적은
   하나의 기능 요청에 포함됐더라도 별도 커밋 후보로 검토한다.
4. 구현과 직접 관련된 테스트·SSOT 문서는 해당 구현과 같은 커밋에 두어 각 커밋이 완결되게 한다.
5. 같은 파일에 여러 목적의 변경이 있으면 부분 스테이징하고, 각 staged diff가 한 가지 목적만 설명하는지 확인한다.
6. 각 커밋 직전에 포함 파일과 diff를 검토하고 해당 범위의 검증을 실행한다.

커밋 개수를 늘리기 위해 파일마다 기계적으로 나누거나, 함께 있어야 빌드·테스트·계약이 완결되는 코드와 테스트·문서를 분리하지 않는다.
반대로 “같은 기능”이라는 이유만으로 독립적인 기반 구조, 저장소 연동과 API 동작을 하나의 큰 커밋에 합치지 않는다.

일반 커밋과 푸시는 사용자의 명시적 요청으로 진행할 수 있다.
`AGENTS.md`의 보호 조건에 해당하는 Git 작업은 보호 경로를 따른다.

---

## 7. 작업 기록

일반·보호 작업은 `docs/dev/tasks/`의 파일 하나에서 계획과 결과를 함께 관리한다.
경량 작업과 읽기 전용 작업은 기록하지 않는다.

작업 기록은 다음 네 부분만 기본으로 사용한다.

1. 작업 목적
2. 변경 범위와 계획
3. 변경 결과
4. 검증과 남은 사항

보호 작업은 여기에 승인 내용, 대상 환경과 복구 수단을 필요한 위치에 추가한다.
고정된 작업 상태, Attempt 번호, `PASS`·`FAIL`·`BLOCKED` 분류와 별도 마감 절차는 요구하지 않는다.

작업이 끝나도 파일을 다른 폴더로 이동하지 않는다.
기존 이슈, PR, ADR 또는 변경 로그가 있으면 작업 기록에서 관련 링크를 남길 수 있다.
